    How the portal is designed Level: Advanced

    Service design and architecture

    The design artefacts behind this portal: why it exists, how it will be tested with users, how it works and how each requirement is proved.

    In brief

    • Every requirement traces to the pages that meet it and the checks that prove it.
    • The research plan says how each assumption could be proved wrong.
    • The Service Standard rating is a self-assessment, not an assessment.

    Theory of change

    Departments must adopt the DAM Policy, but guidance for its three capabilities is spread across many pages and practitioner packs, so the same facts are recorded several times and returns are assembled late.

    1. Inputs

      • Published GOV.UK guidance behind the policy
      • Practitioner playbooks for governance and quality
      • Open standards (DCAT, MEM, DQV)
      • GitHub for hosting, contact and automation

    2. Activities

      • Join the three capabilities into one method with one set of roles
      • Give each role a route and a learning journey
      • Check sources, accessibility and links automatically every week

    3. Outputs

      • One portal with step-by-step methods, templates and modules
      • Open data versions of every requirement, template and term
      • A public record of defects, open items and health

    4. Outcomes

      • Owners, records and DQAPs are set up once and reused
      • Returns are built from catalogue records, not retyped
      • Practitioners know which requirement each step meets

    5. Impact

      • Critical data assets are owned, findable and fit for use across government
      • Services that rely on shared data, and the people they serve, are less affected by poor data

    Assumptions to test

    • Practitioners will use a single portal if it saves them effort (untested, OR-04)
    • Hand-offs between capabilities reduce duplicate recording (untested)
    • GOV.UK guidance remains the authority and changes are caught weekly

    Research plan

    Questions

    • Can each role find the steps that apply to them in under two minutes?
    • Do the hand-offs match how departments actually organise ownership, cataloguing and quality?
    • Which sector supplements (DD-01 to DD-14) are needed first?
    • Can people with access needs complete a route without help?

    Methods

    • Moderated usability sessions with 5 to 8 people per role, including people who use assistive technology
    • Tree test of the navigation
    • A survey through the Working Group
    • Analysis of feedback received through the contact and feedback forms

    Hypotheses and how they would be disproved

    Hypotheses and falsification conditions
    IDHypothesisDisproved if
    H-01Routes by role reduce time to find the right step.Median time to find a step is not lower on a route than through search alone.
    H-02Recording the owner once and reusing it reduces mismatches.Owner mismatches between register, record and DQAP do not fall after adoption.
    H-03Learning modules improve confidence for new owners and stewards.Self-rated confidence does not rise after completing the role's modules.

    Ethics and consent

    Participants give informed consent, can withdraw at any time, and are recorded only with permission. Notes name roles, not people. No session collects data above OFFICIAL.

    Solution architecture

    Components

    • AC-01 Content file
      content/playbooks.yaml: requirements, methods, roles, personas, modules, sources and registers.
    • AC-02 Generator
      tools/build.py: validates references, writes static pages, open data, sitemap, images.
    • AC-03 Front end
      Static HTML and CSS with one progressive-enhancement script; no external assets; strict Content Security Policy.
    • AC-04 Checks
      tools/check_site.py (static), tools/check_browser.py (Playwright with axe-core), tests/ (vaccinations).
    • AC-05 Health run
      tools/health.py: GOV.UK Content API source dates, review date and page weight; results on the Status page.
    • AC-06 GitHub services
      Actions (build, check, publish, weekly health, CodeQL, release), Pages, issue forms, Discussions, Dependabot.

    Flows

    • Change: pull request -> build -> static checks -> vaccinations -> browser checks -> review -> merge -> Pages
    • Weekly: health run -> Status page -> issue labelled health if something needs a person
    • Contact: contact form -> pre-filled GitHub issue form -> person sends it -> triage

    Data

    No personal data is held. Browser storage keeps progress and display choices on the reader's device only.
